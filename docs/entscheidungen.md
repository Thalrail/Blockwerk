# Entscheidungen Blockwerk (Stand 19.10.2026)
- Programmname: **Blockwerk**. Repo auf GitHub: Konto **Thalrail**, Repo **blockwerk** (eigenes, neues Repo; der Probeplaner bleibt unverändert).
- Server: Aternos, Bedrock. Bauwerke werden NICHT eingespielt/einkopiert, sondern von Hand nach Bauplan (Schicht für Schicht) gebaut.
- Oberfläche: ausschließlich Desktop, keine Handy-App. Gespielt wird auf der PS5, Blockwerk läuft auf PC/Laptop daneben als Bauplan-Bildschirm (Kompaktmodus aus Entfernung lesbar).
- Texturen: Faithful 32x (Bedrock-Fassung), Lizenzpflichten siehe `docs/ebenen.md`, Ebene 5.
- Ebenenmodell: `docs/ebenen.md` (Ebene 0–5 bestätigt).
- Seed: soll später einpflegbar sein (Platzprüfung: passt das Bauwerk an die Stelle, Gelände/Biom über Messpunkte).
- Leser (einzige KI-Stelle): zunächst über Claude-Chat (Briefing-Prompt -> JSON zurückkopieren). API-Schlüssel später optional.
- Tester: Jonah, jederzeit, auch mobil (Minecraft Pocket).
- Zitadelle-Bilder (14) legt Jonah im Repo unter `docs/zitadelle/bilder/` ab.
- Reihenfolge: allgemeine Engine zuerst, Zitadelle als Prüfstein.
- Neubeginn (19.10.2026): Blockwerk wird von Claude Code komplett neu nach dem Ebenenmodell umgesetzt. Der frühere M0/M1-Prototyp und Blockplan werden nicht übernommen.
- Technik: reines JavaScript (ES-Module), keine Abhängigkeiten, Tests mit `npm test` (Node 22), Seite über GitHub Pages ohne Build.
- Offen: Desktop-Umsetzung (eigene Desktop-App oder als Desktop-Fenster installierte Webseite).
- Arbeitsweg: Entwicklung mit Claude Code in der Cloud (claude.ai/code), Arbeit auf eigenem Branch, Abnahme per Pull Request durch Jonah.
- Sicherheit: Keine Zugangsschlüssel (Token, Passwörter) im Chat oder im Repo. Der GitHub-Zugang läuft über die Claude GitHub App.
- Aternos-Server (Angabe von Jonah, 20.10.2026): Simulationsdistanz **4 Chunks**, 20 Ticks pro Sekunde, Chunk 16×16. Steht in `data/server.json`.
- Händler (Angabe von Jonah, 21.10.2026): Dorfbewohner-Händler geben die Items beim Handel **direkt ins Inventar**, sie werden nicht gedroppt. Für Handels-Items ist also keine Auffang-Technik nötig. (Trichter für Lager und Sortierer der Zitadelle sind davon nicht berührt.)
- Wasser/Lava vor Trichter & Blockinhalten (Jonah, 21.10.2026): Als Nächstes in Ebene 1 kam Wasser/Lava.
- Java-Platzhalter für Wasser/Lava (Jonah, 21.10.2026): Die Fließ-Logik (Gefälle-Zählung, Abklingen, „erst nach unten“, Plus-Form um eine Quelle in der Luft) darf vorläufig der Java-Implementierung folgen, weil Bedrock nichts dokumentiert. Ausnahme zu „nie Java übernehmen“, gilt nur bis Jonah getestet hat; bleibt `ungeprüft`.
- Wasser/Lava-Logik (Jonah, 21.10.2026): Die Java-Logik (Gefälle bis zum 5. Block, Abklingen, erst nach unten, Plus-Form um eine Quelle in der Luft) „passt 1 zu 1, so funktioniert es auch in Bedrock“. Die Platzhalter-Ausnahme zu „nie Java übernehmen“ ist damit nicht mehr nötig. Bestätigt aus Erfahrung, nicht durch einen gezielten Spieltest: Status bleibt `ungeprüft`, bis er einen Test im Spiel meldet.
- Java als Ersatz, wo Bedrock schweigt (Jonah, 24.10.2026): Wo es für Bedrock keine ausdrückliche Angabe gibt, gilt die Java-Regel (Wiki, Java-Kategorien) als Platzhalter, mit Status `ungeprüft` und Quelle. Zeigt sich im Spiel ein Fehler (z. B. ein Lichtfehler), wird genau diese Stelle gezielt korrigiert, statt alles vorab zu testen. Ausdrückliche Bedrock-Angaben gehen immer vor. Erste Anwendung: Lichtfilter dünner Blöcke (Fackeln, Schienen, Zäune, Türen, Scheiben, Pflanzen … = wie Luft); Treppen und Halbstufen blockieren in Java nach Form: Blockwerk rechnet sie so (Filter 0, nur die vollen Flächen sperren; Jonah, 24.10.2026); Schnee, Pfade, Kolben bleiben unbekannt (Schranken). Fackel: Stärke 14, Reichweite 13 Blöcke (Wiki, von Jonah bestätigt, nicht im Spiel gemessen).
- Brüter und Dorfbewohner-Transport (Jonah, 25.10.2026): Der **Brüter** ist ein Dorfbewohner-Brüter (Vermehrung in einer Brutkammer). Ursprünglich sollten Bahnhof und Entladestelle die Dorfbewohner aus der Brutkammer per Lore in die Handelszellen fahren. Jonah hat in Bedrock festgestellt, dass der Berufsblock nicht an den nächsten, sondern an **irgendeinen** arbeitslosen Dorfbewohner geht (Wiki: erster Eintrag der gemeinsamen Liste). Folge: In der Brutkammer muss immer jemand beobachten, welcher Dorfbewohner losgeschickt werden muss. Der Brutkammer-Entwurf ist offen; Bahnhof, Entladestelle und Brüter werden bis dahin nicht gebaut (siehe `docs/offene-fragen.md`).

- Autonomer Auftragslauf bis zur Draft-PR (Jonah, 31.10.2026): Mit der Freigabe eines Auftrags arbeitet `/blockwerk-auftrag` **selbstständig bis zur fertigen Draft-PR**: Claude implementiert, **Codex prüft jede abgeschlossene Umsetzung unabhängig**, bestätigte Fehler korrigiert Claude selbst und gibt sie erneut an Codex (**höchstens drei Korrekturschleifen**), **Übernahme und Abschluss nur mit grünem Teststatus und gültigem Review für exakt denselben Codezustand** (technisches Gate in `uebernehmen` und `abschluss`), danach **automatisch Branch `claude/<name>`, Commit, Push und Draft-PR** ausschließlich über das Abschluss-Werkzeug `cli.js abschluss`. **Merge, Force-Push und Push auf `main` gibt es nie automatisch; über den Merge entscheidet allein Jonah.** Rückfrage vorher bei grundlegender Architekturänderung, jeder neuen externen Abhängigkeit, Änderung des Auftragsumfangs und nicht sicher lösbarer Lage. Weitere Regeln: kein Start eines autonomen Laufs mit fremden uncommitteten Änderungen, eindeutig geprüfte PR-Basis, Isolation durch Worktrees und Schutz vor Datenverlust bleiben, **die Berechtigungssperren für `git push` und `gh pr` in `.claude/settings.json` bleiben unverändert** (keine Umgehung über andere Befehle oder Werkzeuge; ist der Abschluss blockiert, stoppt der Koordinator und berichtet). Begründung: Jonahs ursprünglich gewünschtes System (ein Auftrag, danach nur noch die Entscheidung über den Merge); der gesamte schreibende Zugriff liegt in einem getesteten Werkzeug mit festen Argumenten statt in lockeren Berechtigungsmustern. Ersetzt für Commit, Push und PR die Zeile „Multi-Agenten-Orchestrierung“ (30.10.2026). Technik und Restrisiken: `docs/orchestrierung.md`.
- Modell-Routing (Jonah, 31.10.2026): **Haiku** (`blockwerk-entwickler-leicht`) nur für **rein mechanische Änderungen ohne eigene Entscheidungslogik** (Tippfehler, Umbenennen, Kommentar, Doku, Zahl oder Text ändern, ein vorgegebener Einzeltest). **Sonnet** (`blockwerk-entwickler`) **direkt** bei Heuristik, Regex, Zustandslogik, Architekturentscheidungen oder Korrektheitsgarantien. Nach einer fehlgeschlagenen Haiku-Umsetzung bei Bedarf **zu Sonnet eskalieren**, statt mehrere Haiku-Korrekturschleifen zu verbrauchen. **Opus** weiterhin nur mit ausdrücklicher Zustimmung von Jonah. Begründung: Im Alltagstest (31.10.2026, `tools/karte.js abhaengig … funktionen`) brauchte eine kleine Aufgabe mit der Garantie „nie falsch sicher“ vier Haiku-Läufe und drei Korrekturschleifen (rund 175.000 Subagent-Tokens); Zahlen in `docs/token-effizienz.md`.
- Testumgebung und Manipulationserkennung (Jonah, 31.10.2026): `tests-ausfuehren` gibt dem Testprozess nur eine Positivliste an Umgebungsvariablen (keine Zugangsdaten, keine Claude-/Codex-/GitHub-Variablen), ein privates Home und Temp; es wertet nur die letzte, rechnende Testzusammenfassung aus und sperrt den ganzen Lauf, wenn sich während der Tests Hauptbaum, HEAD oder Laufzustand ändern (kein Wiedervertrauen durch erneute Tests). Das ist Bereinigung und Erkennung, **keine Prozessisolation**; echte Isolation ist eine eigene, zukünftige Sicherheitsaufgabe. Der Abgleich der Codex-Reviews mit der Bridge-Datenbank ist zurückgestellt, die Vertrauensgrenze steht in `docs/orchestrierung.md`.
- Gehärteter Abschluss und erneute Integritätsprüfung (Jonah, 31.10.2026): Git-Konfiguration, Hooks, `.git/info`, Worktree-Metadaten und globale Git-Konfiguration gehören zum Manipulationsabdruck; alle Git-Aufrufe von Abschluss, Übernahme und Testprüfung laufen gehärtet (gesäuberte Umgebung, keine Hooks, kein fsmonitor, kein eigenes ssh/askpass; das Anmeldeverfahren bleibt nutzbar); vor `uebernehmen` und vor jedem schreibenden Schritt von `abschluss` wird erneut geprüft, eine Abweichung sperrt den ganzen Lauf dauerhaft. Verbleibende Grenzen: nachträglich schreibende Prozesse und fehlende echte Benutzer-/Prozessisolation (eigene zukünftige Aufgabe). Details: `docs/orchestrierung.md`.
- Ausnahme für die Sperrdatei von Claude Code (Jonah, 12.11.2026): Ein echter Lauf wurde gesperrt, weil `.claude/scheduled_tasks.lock` zwischen Start und Übernahme verschwand (der Dateivergleich des Hauptbaums hasht auch von Git ignorierte Dateien). Ausgenommen wird **genau dieser eine Pfad** (`AUSSER` in `lauf.js`; kein Muster, keine weitere Datei unter `.claude/`); `scheduled_tasks.json`, `settings.json`, Hooks, Agenten und Skills bleiben überwacht, Git-Abdrücke, Nachweise und Laufjournale unverändert geschützt. **Restrisiko bewusst akzeptiert:** Herkunft und Semantik der Datei sind nicht offiziell bestätigt (die Dokumentation von Claude Code nennt sie nicht; Belege: Eintrag unter `# claude-code-runtime` in `.git/info/exclude`, Verhalten im echten Lauf, Community-Issue anthropics/claude-code#33565, Code-Kopie einer Drittquelle, dort JSON mit `sessionId`, `pid`, `acquiredAt`). Angenommen wird: kurzlebige Laufzeitsperre ohne ausführbaren Inhalt; eine Änderung der Datei bleibt unentdeckt. Technik und Tests: `docs/orchestrierung.md`, `test/orchestrierung/laufzeitsperre.orchestrierung.js`.
- Veröffentlichung vorbereiteter Branches (Jonah, 12.11.2026): Ein lokal vorbereiteter Branch `claude/<name>` wird mit **einer** Freigabe veröffentlicht: `cli.js veroeffentlichen-vorpruefung` zeigt Repository, Branch, Ziel `main`, Commit, Diff-Übersicht, Tests, Codex-Review, Remote-Stand und PR und liefert einen Freigabe-Hash; der Aufruf `cli.js veroeffentlichen --branch … --bestaetigt …` steht in `ask` (`.claude/settings.json`), **der Bestätigungsdialog von Claude Code ist das Okay** (keine zusätzliche Frage im Chat; der Hash bindet Repository, Origin-URL, Branch, HEAD, Basis, Diff, Tests, Review mit Befunden und Einstufungen, Titel und Einschränkungen, ersetzt aber keine Berechtigung; Remote-Branch und PR werden vor dem Push gegen die Vorprüfung gehalten). Danach pusht das Werkzeug nur diesen Branch, verwendet die offene PR gegen `main` oder erstellt sie, setzt einen Draft auf „Ready for review“, prüft den PR-Head und wartet auf die Pflichtchecks und den Job `test` aus test.yml; ein erneuter Aufruf setzt nach einem Teilfehler fort. Die Sperren `git push *` und `gh pr *` bleiben, es gibt keinen Merge, kein Force und kein Löschen; Merge macht nur Jonah. Sicherheitsdateien (`.claude/`, `.github/`, `tools/orchestrierung/`, `.gitignore`) lehnt das Werkzeug weiter ab; dafür wäre eine eigene, ausdrücklich beschlossene Freigabe nötig (beschrieben in `docs/orchestrierung.md`, nicht umgesetzt). Nur gegen Test-Remote und `gh`-Attrappe geprüft; der erste echte GitHub-Lauf steht aus. Technik: `docs/orchestrierung.md`.
- Produktvision: universeller Bauplaner, Zitadelle nur Referenz (Jonah, 13.11.2026): Beliebige Bauwerke aus Bildern und Text, optional Technik, Seed, Version, Dimension, Koordinaten und Gelände; danach Bearbeiten (Blöcke, Materialien, Bauteile, Abschnitte), Block- und Schichtanleitungen, Material, Fortschritt, gemeinsames Bauen; gebaut wird von Menschen, nie automatisch eingefügt. Die Zitadelle bleibt komplexes Referenzprojekt und Belastungstest, bestimmt die Prioritäten aber nicht allein. Reihenfolge: Haus-Sonde, Spezifikation erweitern, Eingabe ohne KI, Stile und Paletten, Bearbeitungsmodell, schnellere Planung, Spieltest-Schleife (`docs/roadmap.md`); Seed wird nicht nachgebaut, Gelände über Messpunkte; offen: Referenzbauten und Bearbeitungsmodell.
- Bearbeitungsmodell B (Jonah, 13.11.2026): Hybrid, verbindlich für die Architekturplanung; Umsetzung erst im eigenen Arbeitspaket. (1) Einzelblockänderungen werden relativ zu einem stabil identifizierten Bauteil mit lokaler Position und Orientierung gespeichert. (2) Technikblöcke dürfen bearbeitet werden; jede Änderung, die technische Funktionen beeinflussen könnte, löst eine erneute Prüfung aus, eine nicht mehr bestätigte Funktion wird nicht weiter als funktionsfähig angezeigt. (3) Mehrspieleränderungen gehören zu einer gemeinsamen, versionierten Planfassung; Konflikte werden nie stillschweigend überschrieben. (4) Bei verwaisten Blockänderungen entscheidet der Benutzer, kein automatisches Verwerfen oder Verschieben. (5) Die Link-Begrenzung (200.000 Zeichen) wird als technische Einschränkung dokumentiert; eine tragfähige Projekt-Speicherung wird später konzipiert. Befund der Haus-Sonde dazu: die Teil-Nummern (T1, T2 …) sind nicht stabil und taugen nicht als Anker; die Spezifikations-Id ist ein Kandidat, ihre Eignung wird im Arbeitspaket geprüft (`docs/haus-sonde.md`).
- Einbau-Architektur B + C (Jonah, 13.11.2026): Innenräume als freie Zonen (B) und allgemeine Aussparungen (C) als zusammenhängendes Konzept, keine feste Treppe im Raum als Dauerlösung. Erste Treppe gerade, Wendeltreppe später ohne Architekturumbau; Trennwände und Türen von Anfang an als unabhängig platzierbare Bauteile; leere Raumvolumen verursachen keine Blockkollision, ein Block gehört weiter höchstens einem Teil; Aussparungen, Öffnungen und spätere Einzelblockänderungen auf gemeinsamer Grundlage; alles deterministisch und mit dem Ebenenmodell vereinbar. Untersuchung und Paketzerlegung: `docs/architektur-einbau.md`; Umsetzung erst nach Freigabe je Paket.
- Rahmenursprung und Ebene 0 (Jonah, 14.11.2026): Entscheidung 1 bestätigt: Ebene 0 bleibt unverändert, Zellenlisten laufen über den Vermesser mit Platzhalterblöcken. Entscheidung 3 bestätigt unter der Bedingung, dass die Konvention eindeutig dokumentiert und konsistent ist. Konvention (`docs/architektur-einbau.md`, Abschnitt 3.6): Ursprung des Referenzrahmens eines Teils = Ecke Nordwest unten (kleinstes x, y, z) des Quaders um die Blöcke des Pakets in der Null-Lage, ohne Aussparungen und Änderungen; Rahmenzellen sind ganze Zahlen ≥ 0 für Blöcke (Aussparungen dürfen negativ sein). Drehung (0–3) und Verschiebung gelten nur über die Lage des Teils und lassen die Rahmenzelle unverändert; bei Größenänderung bleibt die Nordwest-Ecke die Verankerung (Änderungen an derselben Rahmenzelle bleiben, was nicht mehr im Teil liegt, wird verwaist). - Wand-Ausrichtung und Projektkennung (Jonah, 14.11.2026): (1) Bei `wand-nord|ost|sued|west` ist die Wandseite verbindlich (Kind schaut nach außen); eine zusätzliche `lage.ausrichtung` lehnt der Prüfer der Spezifikation mit einer Rückfrage ab („weglassen“), die Übersetzung folgt in jedem Fall der Wandseite. - Materialwahl in der Spezifikation (Jonah, 14.11.2026): Zu U4 der Oberfläche zum Bearbeiten wählte Jonah Option B: Neben der Stimmung kann die Spezifikation von Hand eine Materialwahl enthalten, optional `projekt.stil` und `teile[].stil` mit `stimmung` und `palette` (Rolle Wand, Akzent, Boden, Licht, Glas auf einen Registerblock, je Form voll, treppe, tuer, scheibe). Das ist ein Ausnahmefall vom Grundsatz „Spezifikation ohne Blöcke“: Die Materialwahl gilt als WAS (Aussehen, vom Benutzer gewünscht), nicht als WIE (Koordinaten, Schaltungen); Technikblöcke bleiben fest. Sie wird nur von Hand gesetzt; Leser und Briefing-Prompt füllen oder nennen sie nie. Die Regeln des Designers (`plan.palette`: Block im Register, kein Arbeitsblock, Form passt, drehbar, Licht leuchtet) gelten unverändert und prüft schon der Prüfer der Spezifikation (Rückfrage mit Pfad statt Absturz). - Zulassung im Planfassungsformat (Jonah, 14.11.2026): Zu U6 bestätigte Jonah, dass `zugelassen: true` Bestandteil der gemeinsamen, versionierten Planfassung wird. Verbindliche Regeln: (1) Die Zulassung bedeutet ausschließlich, dass eine verwaiste Änderung bewusst akzeptiert wurde; sie bestätigt weder die erfolgreiche Anwendung noch die technische Funktionsfähigkeit (der Status der Änderung und die Technikbestätigung bleiben unberührt). (2) Sie ist jederzeit widerrufbar. (3) Alle Teilnehmer einer gemeinsamen Planfassung sehen dieselbe Zulassung (sie gehört zum Inhalt, den der Raum je Zelle vergleicht und rundsendet). (4) Ältere Versionen dürfen die Information nicht stillschweigend beim erneuten Speichern oder Synchronisieren entfernen: eine erkennbare Formatprüfung lässt sie solche Fassungen sichtbar ablehnen. Umsetzung: Browser-Speicher mit Zulassungen als `{ format: 2, planfassung }` (ältere Versionen finden keine gültige Planfassung, legen eine Kopie unter „….defekt“ an und melden es), Link und Datei mit Umschlag `version: 2` (ältere Versionen: „Version 2 wird nicht verstanden“), im Raum der Vergleich je Zelle (ein älterer Klient bekommt einen Konflikt statt zu überschreiben) und die Angabe `format` des Dienstes (ein älterer Dienst kennt keine Zulassungen: die Seite sendet sie ihm nicht). Gegen den echten Stand vor U6 geprüft. Ohne Zulassung bleibt alles Format 1. Technik: `src/ebene5/planfassung.js`, `docs/referenz/stand-ebene5.md` (U6).
